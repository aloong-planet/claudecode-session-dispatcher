# ADR-0002: A session that compacts itself is woken by the plugin's mod, or by a hook where the mod does not run; the server, the hooks and the mod are one plugin

- Status: Proposed

## Context

A compaction started by `/compact` leaves a session idle, so a session that compacts itself with `compact_self` needs something to make it carry on. The server did this itself: after the tool had returned it read the session's transcript, waited for the compaction record and for the session to be idle, and typed `continue` into its window. It typed nothing when the session was not idle within 60 seconds of the record, or when no compaction was recorded within 30 minutes; the session then stayed stopped and nobody was told. Claude Code runs `PostCompact` hooks when a compaction has finished, and a command hook declared with `asyncRewake` that exits with code 2 makes an idle session start a turn. A hook has to be declared where every session reads it. The server has to reach every session too; one user-level MCP registration was planned for that and was never made.

Claude Code also loads a plugin's hooks module, its mod, into the session's own process. A mod can answer a tool call in the tool's place, ask Claude Code to compact the conversation between turns, and submit a prompt that starts a turn. With a mod a session can compact itself and carry on with nothing typed into a window, in any terminal. This was found on 2026-11-12, after the hook had been built and merged and before the plugin was installed in the owner's configuration.

## Options

1. **Where the plugin's mod runs in a session, the mod answers `compact_self`, compacts the conversation when the turn ends and starts the next turn itself. Everywhere else the server types `/compact` and a `PostCompact` hook wakes the session. The server, the hooks and the mod are one Claude Code plugin, which the owner installs once at user scope from a marketplace in the repository, and which the start-up command loads with `--plugin-dir` where that installation does not reach the dispatcher session.**
2. The server keeps typing `continue` once it sees the session idle. Rejected by the owner on 2026-11-11: it keeps the two cases above in which the session stays stopped.
3. The hook wakes the session, and the server's typing stays as a fallback for a session without the hook. Rejected: there are two mechanisms to maintain and test, and on the fallback path both time limits remain, as does the moment before the typing in which a message that arrives has its turn interrupted.
4. The hook is declared in the user-level `settings.json` and the server keeps a user-level MCP registration, so that tool names stay as they were. Rejected: the two are installed separately, so a session can have the server without the hook, and such a session is not woken; it also means editing the owner's settings file.
5. The plugin of option 1, with the start-up command still passing the server by `--mcp-config`. Rejected: Claude Code then connects the server once, under the `--mcp-config` definition, so the same tool has one name in a dispatcher session and another in every other session, and documents and permission rules would carry both.
6. The plugin of option 1, with the start-up command relying on the installed plugin alone. Rejected: without the installation a dispatcher session has no tools, and the command would have to check for the installation and refuse to start.
7. The plugin of option 1, installed by a symbolic link in `~/.claude/skills/` instead of a marketplace. Rejected: the documentation does not say whether a symbolic link counts, and it was not measured; such a plugin has the id `<name>@skills-dir`, which some management settings treat differently.
8. The plugin of option 1, with the repository's root as the plugin's directory. Rejected: Claude Code puts the files in `bin/` at a plugin's root on the `PATH` of the Bash tool in every session that has the plugin, which would hand `claude-dispatcher` to all of them. The plugin's directory is `plugin/`, and its declarations reach the programs in the repository from there.
9. The plugin of option 1 under the name `claude-session-pool`, after the product. Chosen first, on 2026-11-11, and rejected by the owner on 2026-11-12: `claude plugin validate` refuses a plugin name that starts with `claude-`, as one that passes for Anthropic's own. Claude Code 2.1.322 still installs and loads a plugin under such a name, but the validator could then not serve as a check of the manifest, and a later version might refuse the name where it matters.
10. The hook alone wakes the session, with no mod. This was the decision of 2026-11-11 and is what was built first. Set aside by the owner's choice of option 1 on 2026-11-12: it works only in Terminal windows, it types into the session's window, and the model reads the wake as a hook's blocking error.
11. The mod compacts and the hook stays the only waker: the mod leaves a wake request before it asks for the compaction. The agent recommended this first and withdrew it on 2026-11-12. When a compaction fails, is vetoed or is cancelled, no `PostCompact` hook runs, so the mod would have to start the turn itself in those cases anyway; and the hook wakes only a conversation that has a wake request, so leaving none on the mod's way already prevents a second wake.
12. The mod alone, with the typing, the two hooks, the hook records and the wake requests removed. Rejected by the owner on 2026-11-12, who kept the hook: a session in which the mod does not run would have no way to compact itself.
13. The mod registers a tool of its own beside the server's `compact_self`. Rejected by the owner on 2026-11-12: the model would have to choose between two tools, and the written rule that names `compact_self` would have to follow.
14. The model writes the text its next turn starts with, as an argument of `compact_self`. Rejected by the owner on 2026-11-12, as it was for the hook on 2026-11-11: the hook's way has no such argument, so the two ways would behave differently, and the summary of the compaction already carries the state of the work.

## Decision

We wake a session after a compaction it asked for in one of two ways, by the mod where it runs and by a `PostCompact` hook everywhere else, and we deliver the server, its hooks and the mod as one Claude Code plugin (option 1).

- In an interactive session in which the mod runs, the mod answers the call to `compact_self` in the server's place. When the turn ends with the model's answer, it asks Claude Code to compact the conversation, and when that has finished it submits one fixed sentence as a prompt, which starts a turn. It leaves no wake request, so the hook stays quiet after this compaction. When an earlier call that the server handled left one in the conversation, the mod starts no turn after the compaction and the hook wakes the session, so that it is woken once. When the compaction does not complete, the mod starts a turn with a sentence that says so. When the owner interrupts the turn or cancels the compaction, the mod does nothing more.
- In every other session the call reaches the server. `compact_self` leaves a wake request for its conversation before it types `/compact`. The hook is declared with `asyncRewake`. When the compacted conversation has a wake request, the hook exits with code 2, and Claude Code starts a turn and hands the model one fixed sentence. After `compact_self` has returned, the server does nothing more.
- A second hook, on `SessionStart`, records that the plugin's hooks run in a session. A `compact_self` call the server handles is refused when no such record exists for the attached session.
- The plugin is named `cc-session-pool` and its server `pool`. Every session gets the plugin from one installation at user scope, which the owner makes from a marketplace of the same name in the repository. That installation replaces the planned user-level MCP registration. The dispatcher session gets it from the installation too when the installation is enabled in its directory and reads the start-up command's own repository; otherwise, or when the command cannot find that out, the command loads the plugin with `--plugin-dir` for the dispatcher session.

This record stays Proposed until the plugin has been installed in the owner's own configuration and a session there, started without the start-up command, has compacted itself and been woken. What the decision first rested on from the documentation alone has been measured since: under a throwaway configuration directory the plugin, installed at user scope from the local marketplace, is used in place, and a plugin given with `--plugin-dir` takes the place of the installed plugin of the same name; in a real Terminal window, with the plugin loaded by `--plugin-dir`, a session compacted itself and the hook woke it. The mod's way was measured on 2026-11-12 with a copy of the plugin that carried a trial mod beside the hooks, loaded by `--plugin-dir` in a session outside Terminal: the mod answered the call, the conversation was compacted, the session started one turn, and the hook ran and stayed quiet.

## Consequences

- Positive: where the mod runs, nothing at all is typed, the session need not run in a Terminal window, and none of the refusals of the typing way applies.
- Positive: the mod learns how the compaction ended, so a compaction that failed or was vetoed is reported to the model in a new turn instead of leaving the session stopped.
- Positive: the model reads the mod's sentence as a message the plugin sent, not as a hook's blocking error.
- Positive: on the hook's way too, a session is woken at the moment its compaction finishes, with nothing typed into its window after the command. The 60-second and 30-minute waits are gone, and with them the two cases in which a session stayed stopped because a wait had run out.
- Positive: the server keeps no wait running after `compact_self` has returned.
- Positive: a session that has the tool has the hooks and the mod, because one plugin carries all three, and a tool has the same name in every session.
- Positive: a plugin listed in a marketplace that was added from a local directory is used in place, so a change in the repository reaches every session started after it.
- Negative: there are two ways to compact and wake, and both have to be maintained and tested; option 3 was rejected for exactly that. The hook's way is taken only in a session in which the mod does not run, so a defect in it can stay unnoticed for long.
- Negative: the mod rests on Claude Code's interface for mods, which was measured on Claude Code 2.1.322. The mod tells the owner's cancellation of a compaction from a failure by the wording of Claude Code's message; if a later version words it differently, the mod reports a cancellation as a failure and starts a turn the owner did not want.
- Negative: a request the mod holds lives in the session's process only. A session that ends before the turn does is not compacted when it is resumed. A reload of the mod, which a save under a `--plugin-dir` directory causes, loses it too, and once a compaction has started it can leave the session compacted and not woken; the owner left the fix to a later change.
- Negative: the mod reads the server's wake requests to decide whether to wake the session itself, so it depends on their location and form, which `src/wake.ts` defines; the two have to change together.
- Negative: every tool is renamed to `mcp__plugin_cc-session-pool_pool__<tool>`. Whatever names a tool, such as a permission rule or a written procedure, has to follow.
- Negative: Claude Code hands the model the hook's sentence as `Stop hook blocking error from command "PostCompact:manual": …`. The sentence therefore has to say that it is not an error, and whether the session carries on depends on how the model reads it. Of the four wakes that were measured, the model carried on as it had been asked to in three.
- Negative: the wake rests on behaviour that Claude Code's documentation does not state for this event: the hooks page describes `asyncRewake` in general and does not say that it applies to `PostCompact`. It was measured on Claude Code 2.1.322. If a later version changes it, a session that compacts itself stays stopped, and nothing reports that.
- Negative: the start-up command decides whether to load the plugin itself from the output of `claude plugin list --json`, which Claude Code's documentation does not state as a stable interface; it was measured on Claude Code 2.1.322. When the output cannot be read the command loads the plugin with `--plugin-dir` and says why, so the dispatcher session keeps its tools, because a plugin given with `--plugin-dir` takes the place of an installed plugin of the same name.
- Negative: a session in which neither the mod nor the plugin's hooks run cannot compact itself, because `compact_self` refuses there. Hooks that are switched off after the record was written are not detected, and such a session stays stopped after its compaction.
- Negative: there are two more kinds of file under `~/.claude-session-pool/`, hook records and wake requests. A wake request does not lapse, so one whose compaction never came makes a later `/compact` that someone types into that conversation wake the session.
- Negative: once the plugin is installed, every Claude Code session of the user runs the plugin's hook at each start, clear and compaction, in addition to the server process that the planned registration would also have started.
- Negative: the plugin works only where Claude Code uses it in place, because the programs its declarations run, and the packages the server needs, lie in the repository outside the plugin's directory. A marketplace from which Claude Code copies the plugin, such as one on a git host, does not work.
- Neutral: the plugin and its marketplace are not named after the product. The repository, the spec, the package and the directory `~/.claude-session-pool/` keep the name `claude-session-pool`.
- Neutral: the installation at user scope is the owner's step and writes to the owner's Claude Code settings. The user-level MCP registration it replaces was never made, so nothing has to be migrated.
- Neutral: `compact` on a slot is unchanged. It still types the command and confirms the compaction from the worker session's transcript.
